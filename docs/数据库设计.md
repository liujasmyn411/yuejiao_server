# 粤教服务 AI Agent 系统 — 数据库设计

## 概述

数据库名称：`yuejiao`  
字符集：`utf8mb4` — 存储引擎：`InnoDB`  
共 15 张表，覆盖用户体系、CRM、教务、留学进度、活动管理、心理关怀、通知、组织架构。

所有表均采用 `delete_flag`（软删除）+ `create_time` / `update_time`（时间戳）规范。

### 逐表关联说明

#### 1. sys_user — 所有业务表的外键锚点

作为统一用户表，`sys_user` 是系统中被引用最广泛的表：

| 子表 | 关联字段 | 关联类型 | 说明 |
|------|---------|---------|------|
| student_admin_service | student_id | 1:N | 一个学生可提交多条请假/考务申请 |
| student_admin_service | approver_id | N:1 | 审批人指向员工用户 |
| student_psych_profile | student_id | 1:1 | 每个学生有且仅有一份心理画像 |
| student_psych_alert | student_id | 1:N | 一个学生可有多条预警记录 |
| student_psych_alert | teacher_id | N:1 | 负责老师指向员工用户 |
| student_feedback_ticket | student_id | 1:N | 一个学生可提交多条反馈工单 |
| student_feedback_ticket | handle_user_id | N:1 | 处理人指向员工用户 |
| student_score | student_id | 1:N | 一个学生有多门课程的成绩记录 |
| student_score | teacher_id | N:1 | 录入老师指向员工用户 |
| student_academic | student_id | 1:N | 一个学生有多条教务DDL记录 |
| student_academic | related_id (via admin_service) | N:1 | 请假记录可关联到具体教务事项 |
| student_study_abroad_progress | student_id | 1:N | 一个学生有7个留学阶段记录 |
| crm_lead | owner_employee_id | N:1 | 每个意向客户归属一名员工 |
| employee_daily_report | employee_id | 1:N | 一个员工有多条日报记录 |
| notification | recipient_id | 1:N | 一个用户可收到多条通知 |
| event_lecture | creator_id | N:1 | 活动创建人指向员工用户 |

**关键设计点：学生 ↔ 班主任**
- `sys_user.head_teacher_id` 是学生与班主任之间的自引用外键
- 学生（user_type=STUDENT）的 head_teacher_id 必填，指向 user_type=EMPLOYEE 且 employee_role=班主任 的用户
- 这是请假审批路由的核心：请假申请提交后，系统通过 `student_id → sys_user.head_teacher_id` 找到对应班主任作为审批人

#### 2. student_admin_service — 请假/考务与教务的关联

- `student_admin_service.related_academic_id → student_academic.id`
- 当学生因某次考试或DDL请假时，请假记录可关联到具体的教务条目
- 这样班主任审批时能看到"该生因XX考试申请请假"，做出更合理的审批决策

#### 3. 心理关怀域的表内关联

```
student_psych_profile (画像, 1:1)
       ↕ 通过 student_id 关联
student_psych_alert   (预警, 1:N)
```

- `student_psych_profile` 存储学生的心理画像快照（最新情绪标签、风险等级、累计预警次数）
- `student_psych_alert` 存储每次预警的详细记录（触发原因、来源、处理过程）
- 当 alert 表新增一条记录时，profile 表的 `total_risk_count` +1，`risk_level` 同步更新
- profile 是读优化表（快速查询学生心理状态），alert 是写优化表（记录每笔预警流水）

#### 4. 活动域的 1:N 关联

```
event_lecture (活动) ── 1:N ──→ event_registration (报名)
```

- `event_registration.event_id → event_lecture.id`
- 一场活动可有多个报名记录
- `event_lecture.current_participants` 为冗余计数，通过报名记录的增删动态维护
- `event_registration.customer_id` 可关联到 `crm_lead.id`（意向客户报名活动）或 `sys_user.id`（在读学生报名）

#### 5. 组织架构的树形自引用

- `org_department.parent_id → org_department.id`（0 表示顶级部门）
- 通过 parent_id 自引用形成公司 → 部门 → 小组的三级树形结构
- `org_department.manager_id → sys_user.id`，部门负责人必须是员工用户

#### 6. 通知表的多态关联

- `notification.recipient_id → sys_user.id`（通知接收人）
- `notification.related_id` 为多态外键，根据 `notification_type` 关联到不同业务表：
  - `leave_approved / leave_rejected` → `student_admin_service.id`
  - `feedback_resolved` → `student_feedback_ticket.id`
  - `system` → 无关联业务ID

## 需求驱动的表设计决策

### 业务需求分析与建表推导

本项目"粤教服务 AI Agent 系统"服务于留学教育机构，核心业务场景包括：**学生日常管理、教务考试追踪、留学申请进度、客户意向转化、员工工作管理、活动运营、心理健康关怀**。以下逐场景推导建表决策。

### 场景一：用户体系（1 张表）

**需求：** 系统需要统一的账号体系，学生、员工、管理员使用同一登录入口，但角色权限不同。学生需要绑定班主任用于请假审批。

**推导过程：**
- 传统方案是学生表 + 员工表分表存储，但会导致登录模块需要判断两张表，且通知、权限等公共逻辑需要写两套
- 采用统一用户表（sys_user），通过 `user_type` 字段区分身份，`employee_role` 细化员工职能
- 学生与班主任的关系通过自引用外键 `head_teacher_id` 实现，一条 SQL 即可查出学生的班主任信息

**决策：1 张 `sys_user` 表，而非学生表 + 员工表分开。**

### 场景二：学生行政服务（1 张表）

**需求：** 学生可以提交请假申请（病假/事假），班主任审批；同时支持考务相关的申请。

**推导过程：**
- 请假和考务的核心字段高度重合（申请人、申请原因、审批人、审批状态）
- 通过 `service_type` 字段区分请假 / 考务即可，无需分两张表
- `leave_type` 仅在 service_type=请假 时有意义，考务场景下为 NULL

**决策：1 张 `student_admin_service` 表统一管理请假和考务申请。**

### 场景三：心理健康关怀（2 张表）

**需求：** AI 通过聊天对话检测学生情绪波动，自动生成预警；同时老师可以手动记录心理观察。需要学生心理画像总览 + 预警明细。

**推导过程：**
- 读场景（心理状态总览）和写场景（预警流水）的查询模式完全不同
- 如果只用一张预警表，每次查学生心理状态都要聚合计算，高频查询效率低
- 采用读写分离设计：
  - `student_psych_profile`（1:1 画像表）— 缓存最新状态，O(1) 查询
  - `student_psych_alert`（1:N 预警表）— 记录每笔预警流水，支持追溯

**决策：2 张表，读写分离，profile 作为 alert 的聚合快照。**

### 场景四：学生反馈工单（1 张表）

**需求：** 学生可提交投诉、建议、咨询，员工处理后反馈结果。

**推导过程：**
- 反馈工单是独立业务域，与请假/教务无强关联
- 字段集合独立：反馈类型、紧急程度、处理方案、通知状态
- 流程独立：待处理 → 处理中 → 已处理，与请假审批流不同

**决策：1 张独立的 `student_feedback_ticket` 表。**

### 场景五：教务与成绩（2 张表）

**需求：** 录入学生考试成绩，同时管理考试、论文、作业等教务事项的DDL截止日期。

**推导过程：**
- 成绩和教务DDL虽然都与"学期/课程"相关，但本质是两种实体：
  - 成绩（student_score）：**结果数据**，考试结束后的分数记录
  - 教务DDL（student_academic）：**待办数据**，考试前的安排信息（地点、时长、截止日期）
- 成绩表关注"得分/及格线/排名"，教务表关注"截止日期/提醒/完成状态"
- 如果合并为一张表，会导致大量 NULL 字段（成绩没出来前教务字段有值，考试结束后成绩字段才有值）

**决策：2 张表，成绩表 + 教务DDL表分离。**

### 场景六：留学进度追踪（1 张表）

**需求：** 留学申请有标准化的 7 个阶段（文书准备→文书审核→院校申请→院校反馈→录取结果→签证办理→行前准备），每位学生的每个阶段都需要独立追踪。

**推导过程：**
- 每个学生的 7 个阶段是固定流程，但每个阶段的进度、负责人、完成时间是独立的
- 方案A：一张表，每个学生一行，7 个阶段的进度用 JSON 存储
  - 缺点：无法按阶段筛选（如"查询所有在签证办理阶段的学生"），更新需要整行锁
- 方案B：一张表，每个学生的每个阶段一行（1 个学生 = 7 行）
  - 优点：每个阶段独立追踪，可按阶段筛选、排序，可独立分配负责人

**决策：1 张 `student_study_abroad_progress` 表，`stage_order` 1-7 标识阶段顺序，`is_current` 标记当前阶段。**

### 场景七：CRM 意向客户管理（1 张表）

**需求：** 市场专员跟进潜在意向客户，记录客户背景、意向国家/专业、跟进历史、意向评分。

**推导过程：**
- 意向客户与学生是不同的实体：客户尚未入学，学生已在读
- 客户转为学生后，信息从 crm_lead 同步到 sys_user（新建学生账号），crm_lead 状态变为"已签约"
- 如果将客户和学生放同一张表，会导致大量字段对客户无意义（班级、成绩等），对学生也无意义（意向国家、跟进历史等）

**决策：1 张独立的 `crm_lead` 表，通过 `owner_employee_id` 关联负责员工。**

### 场景八：员工日报（1 张表）

**需求：** 员工每日提交工作日报，AI 自动生成摘要。

**推导过程：**
- 日报是独立的日常工作记录，字段少（日期、类型、内容、摘要）
- 与 CRM（跟进记录）有交集但目的不同：日报是个人工作汇总，CRM 跟进记录是客户维度的交互历史
- AI 摘要功能需要独立的文本字段，不宜混入其他表

**决策：1 张 `employee_daily_report` 表。**

### 场景九：产品与活动（3 张表）

**需求：** 展示留学课程项目，同时支持线上线下活动的发布、报名、签到。

**推导过程：**
- 课程项目（course_project）：静态展示内容，类似产品目录，用于学生浏览选择合适的留学项目
- 活动讲座（event_lecture）：有时效性的运营活动，包含报名截止、人数上限、签到等动态管理
- 活动报名（event_registration）：活动与参与者之间的 N:N 关系（一人可报多个活动，一个活动有多人报名）

**决策：3 张表——课程项目表 + 活动表 + 报名表。** 课程项目和活动分开是因为前者是静态产品，后者是动态运营事件，生命周期完全不同。

### 场景十：组织架构与通知（2 张表）

**需求：** 管理公司的部门层级结构，同时支持站内通知推送。

**推导过程：**
- `org_department`：通过 parent_id 自引用实现树形部门结构，3 级（公司→部门→小组）
- `notification`：统一的站内通知，通过 `notification_type` 区分通知来源（请假审批结果、反馈处理结果、系统通知），`related_id` 多态关联到具体业务记录

**决策：2 张表——组织架构表 + 通知表。**

### 汇总：15 张表的决策逻辑

| 序号 | 表名 | 业务域 | 建表驱动因素 |
|------|------|--------|-------------|
| 1 | sys_user | 用户体系 | 统一账号（学生+员工+管理员合一），避免多表登录 |
| 2 | student_admin_service | 学生行政 | 请假+考务字段重合度高，service_type 区分即可 |
| 3 | student_psych_profile | 心理关怀 | 读优化——心理画像快照，O(1) 查询 |
| 4 | student_psych_alert | 心理关怀 | 写优化——预警流水记录，支持追溯 |
| 5 | student_feedback_ticket | 学生服务 | 独立业务域，流程和字段与请假不同 |
| 6 | student_score | 教务成绩 | 结果数据——考试后的分数，关注得分/及格 |
| 7 | student_academic | 教务DDL | 待办数据——考试前的安排，关注截止/提醒 |
| 8 | student_study_abroad_progress | 留学进度 | 7 阶段独立追踪，每阶段一行便于筛选和分配 |
| 9 | crm_lead | CRM | 客户≠学生，分开存储避免字段膨胀 |
| 10 | employee_daily_report | 企业办公 | 独立日常工作记录，AI 摘要需独立字段 |
| 11 | course_project | 产品展示 | 静态产品目录，与动态活动生命周期不同 |
| 12 | event_lecture | 活动运营 | 动态事件管理，包含报名截止、签到 |
| 13 | event_registration | 活动运营 | 活动与参与者的 N:N 关联 |
| 14 | org_department | 组织架构 | 树形部门结构，自引用 parent_id |
| 15 | notification | 通知系统 | 统一站内通知，多态关联各业务表 |

### 关键设计原则

1. **统一身份 > 分表存储**：学生和员工共用一个用户表，避免多套登录和权限逻辑
2. **读写分离**：心理关怀域拆分为画像（读）和预警（写），以查询模式驱动分表
3. **实体独立**：客户≠学生，成绩≠教务，课程项目≠活动——本质不同的实体不硬凑
4. **枚举优于分表**：请假/考务用 service_type 枚举区分，不额外建两张表
5. **行优于列**：留学 7 阶段用 7 行而非 7 列或 JSON，保证可筛选性和扩展性
6. **冗余可控**：仅在读多写少场景（心理画像、活动报名计数）接受少量冗余，其余严格遵循 3NF

## 实体关系概览

```
sys_user (统一用户)
  ├── 1:N → student_admin_service (请假)
  ├── 1:N → student_psych_alert (心理预警)
  ├── 1:1 → student_psych_profile (心理画像)
  ├── 1:N → student_feedback_ticket (反馈工单)
  ├── 1:N → student_score (成绩)
  ├── 1:N → student_academic (教务DDL)
  ├── 1:N → student_study_abroad_progress (留学进度)
  ├── 1:N → crm_lead (归属客户) [as EMPLOYEE]
  ├── 1:N → employee_daily_report (日报) [as EMPLOYEE]
  └── 1:N → notification (通知)

event_lecture (活动)
  └── 1:N → event_registration (报名)

org_department (组织架构)
  └── 自引用 parent_id 形成树形结构
```
