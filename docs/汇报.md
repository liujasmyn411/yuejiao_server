# 粤教服务 AI Agent 系统 — 技术汇报

## 一、项目概况

粤教服务 AI Agent 系统是一个面向国际教育服务行业的智能对话平台，服务三类用户：外部访客（客服）、内部员工（企业办公）、在册留学生（学生服务）。采用 **FastAPI + LLM + RAG + 规则引擎** 混合架构，共 15 张数据表、43 个 API 端点。

| 维度 | 说明 |
|------|------|
| 框架 | FastAPI (Python) |
| 数据库 | MySQL 8.0 / SQLite，SQLAlchemy ORM |
| 大模型 | GPT-4o-mini（OpenAI 兼容接口，可替换为 DeepSeek/通义千问等） |
| 语音 | Whisper-1 (STT) + TTS-1 (TTS)，复用 OpenAI 接口 |
| 认证 | JWT (HS256) + bcrypt 密码哈希 |
| 部署 | Uvicorn，单进程多 worker 或 Docker |

## 二、各模块技术方法详解

### 2.1 统一对话路由（意图识别）

**文件：** `api/chat_routes.py`

**方法：LLM 意图分类 + 本地关键词兜底（双通道）**

```
用户输入
  │
  ├─ 通道1（优先）：LLM 意图分类
  │   model: GPT-4o-mini
  │   temperature: 0.1（低温度保证分类稳定）
  │   max_tokens: 200
  │   输入：TOP_LEVEL_INTENTS 描述 + 用户消息
  │   输出：{"intent": "customer/enterprise/student", "confidence": 0.95, "entities": {}}
  │
  └─ 通道2（兜底）：本地关键词匹配
      方法：词袋模型 + 角色过滤
      游客只匹配 CUSTOMER_KW / CHITCHAT_KW
      学生匹配 STUDENT_KW / CUSTOMER_KW / CHITCHAT_KW
      员工匹配 ENTERPRISE_KW / CUSTOMER_KW / CHITCHAT_KW
      短输入（≤4字）且无业务词 → 归类为闲聊
```

**用到的技术：**
- LLM 分类（zero-shot，通过 prompt 描述意图）
- 本地关键词词袋匹配（无 ML 模型）
- 角色感知过滤

### 2.2 RAG 检索引擎 — 知识库检索如何达到？

**文件：** `knowledge_base/vectorizer.py`、`loader.py`、`splitter.py`

**结论：没有使用 Embedding / 向量数据库 / 语义检索。本质是一套完整的传统信息检索系统：n-gram 分词 → 倒排索引 → 同义词扩展 → IDF 加权 → 多因子打分排序。所有计算在 CPU 内存中完成，零外部依赖，200 行纯 Python 实现。**

#### 第一步：离线建库（启动时一次性完成）

**1a. 加载原始文件**

```
loader.py → 扫描 knowledge_base/data/ 下所有 .txt/.md 文件
  ├─ 文件名含"问答对" → load_qa_pairs() 解析为 [{"question": ..., "answer": ...}, ...]
  │   支持两种格式：
  │     - Tab 分隔: Q\t\tA（每行一对）
  │     - 标记格式: Q：... A：...（正则提取）
  └─ 其他文件 → load_documents() 读取全文
```

**1b. 对 FAQ 建倒排索引（核心加速结构）**

```python
# 每条 FAQ 的问题文本 → n-gram 分词 → token 集合
for idx, qa in enumerate(self.qa_pairs):
    tokens = self._tokenize(qa["question"])  # 如 {"报名", "流程", "报名流程", "留学"}
    self._faq_tokens.append(tokens)

    # 每个 ≥2 字的 token → 倒排索引: {"报名": {0,3,5}, "流程": {0,7}, ...}
    for t in tokens:
        if len(t) >= 2:
            self._keyword_index[t].add(idx)
```

倒排索引示意：输入一个词，O(1) 查出包含它的所有 FAQ 编号。

**1c. 对普通文档做切片**

```python
split_text(doc["content"], chunk_size=400, overlap=40)
# 按 400 字切分，重叠 40 字保证上下文不丢失
# 优先在句号/换行/分号等自然断点处切开
```

#### 第二步：查询分词 + 同义词扩展

当用户输入 "退费咋办"，处理流程：

```
用户输入: "退费咋办"
  │
  ├─ 1. clean: 去标点 → "退费咋办"
  │
  ├─ 2. n-gram 分词: 1-gram + 2-gram + 3-gram
  │   输出: {"退", "费", "咋", "办", "退费", "费咋", "咋办", "退费咋", "费咋办"}
  │
  ├─ 3. 停用词过滤:
  │   "退" → 不在停用词表中 → 保留
  │   "费" → 不在停用词表中 → 保留
  │   "咋" → 不在停用词表中 → 保留
  │   "办" → 不在停用词表中 → 保留
  │   最终 1-gram: {"退", "费", "咋", "办"}
  │
  │   2-gram 过滤: 所有字都在停用词中才丢弃
  │   "费咋" → 不全是停用词 → 保留
  │   其他同理 → 全部保留
  │
  │   3-gram 过滤: 包含任一停用词就丢弃
  │   "退费咋" → "咋"是停用词 → 丢弃
  │   "费咋办" → "咋"和"办"是停用词 → 丢弃
  │
  │   最终 tokens: {"退", "费", "咋", "办", "退费", "费咋", "咋办"}
  │
  ├─ 4. 同义词扩展 (tokenize_query):
  │   遍历 _SYNONYMS 映射表，在清洗后的文本中匹配:
  │     "咋办" → 命中同义词 → 展开为 "办理"/"申请"/"流程"
  │     "退费" → 命中同义词 → 展开为 "退款"
  │   最终 query_tokens = {"退", "费", "咋", "办", "退费", "费咋", "咋办", "办理", "申请", "流程", "退款"}
  │
  └─ 5. 提取核心词 (≥2 字):
      {"退费", "费咋", "咋办", "办理", "申请", "流程", "退款"}
      区分同义词核心词 {"办理", "申请", "流程", "退款"} 和 n-gram 核心词 {"退费", "费咋", "咋办"}
```

#### 第三步：倒排索引快速召回候选 FAQ

```python
candidate_hits: dict[int, int] = {}  # FAQ编号 → 命中核心词数

for t in core_tokens:  # 遍历每个核心词
    if t in self._keyword_index:  # 在倒排索引中查找
        for idx in self._keyword_index[t]:
            candidate_hits[idx] = candidate_hits.get(idx, 0) + 1

# 至少命中 1 个核心词的 FAQ 进入候选
# 如果一个都没命中 → 所有 FAQ 进入候选（兜底）
```

举例：用户问"退费咋办"，核心词"退款"命中 FAQ #2、#7，"流程"命中 FAQ #2、#5、#9 →
候选集 = {#2 (命中2词), #5 (命中1词), #7 (命中1词), #9 (命中1词)}，而非遍历全部 FAQ。

#### 第四步：多因子排序打分

每条候选 FAQ 按以下公式计算综合分：

```
faq_score = coverage × 0.45 + jaccard × 0.15 + hit_count_bonus + substring_bonus
```

**因子 1：IDF 加权覆盖率 coverage（权重 0.45，主导分值）**

IDF 含义：一个词在越多 FAQ 问题中出现，区分度越低，权重越小。

```python
idf(token) = 1 / (1 + df/total * 10)
# df: 包含该 token 的 FAQ 数
# total: FAQ 总数

# 例如"留学"出现在 80% 的 FAQ 中 → idf("留学") ≈ 0.11（低权重，没啥区分度）
# "退费"只在 5% 的 FAQ 中出现 → idf("退费") ≈ 0.67（高权重，强区分度）
```

```python
# 同义词覆盖率 (权重 0.6)：业务关键词的命中情况
syn_hit = sum(idf(t) for t in syn_core if t in question)
syn_total = sum(idf(t) for t in syn_core)
syn_coverage = syn_hit / syn_total  # 命中关键词的 IDF 占比

# n-gram 覆盖率 (权重 0.4)：辅助匹配
ngram_hit = sum(idf(t) for t in ngram_core if t in question)
ngram_coverage = ngram_hit / ngram_total

# 综合覆盖率 = 同义词 0.6 + n-gram 0.4
coverage = syn_coverage * 0.6 + ngram_coverage * 0.4
```

**因子 2：Jaccard 相似度（权重 0.15，辅助信号）**

```python
jaccard = |query_tokens ∩ faq_tokens| / |query_tokens ∪ faq_tokens|
# 两边共有的词 / 两边合并的词
# 避免覆盖率被高频短词主导，Jaccard 天然惩罚冗余
```

**因子 3：核心词命中加分 hit_count_bonus（上限 0.15）**

```python
syn_hits = sum(3 for t in syn_core if t in question)   # 同义词命中 ×3
ngram_hits = sum(1 for t in ngram_core if t in question) # n-gram命中 ×1
max_possible = len(syn_core) * 3 + len(ngram_core)
hit_count_bonus = min((syn_hits + ngram_hits) / max(max_possible, 1), 1.0) * 0.15
```

**因子 4：精确子串加成 substring_bonus**

```python
if query_text in question:        # "退费" 完整出现在 FAQ 问题中
    substring_bonus = 0.3          # 强信号，大幅加分
elif question in query_text:
    substring_bonus = 0.15
```

#### 第五步：合并结果并截断

```
faq_results (FAQ 精确匹配, top 4) + doc_results (文档模糊匹配, top 5)
  → 按 score 合并排序
  → 截取 top-K
  → 拼接为上下文文本 (max 2000 字符)
```

#### 完整检索示例

用户输入："**德国留学要多少钱**"

```
Step 1 — 分词: {"德","国","留","学","要","多","少","钱","德国","国留","留学","学要",
               "要多","多少","少钱","德国留","国留学","留学要","学要多","要多少","多少"}
  停用词过滤后: {"德国","留学","多少"}  (核心 2-gram 非停用词)
  
Step 2 — 同义词扩展:
  "多少钱" → 匹配同义词 → 展开 "学费"/"费用"/"价格"/"收费"/"总计"
  核心词: {"德国","留学","多少"} + 同义词 {"学费","费用","价格","收费","总计"}
  
Step 3 — 倒排索引召回:
  "德国"   → 命中 FAQ #1,2,4   (德国相关问答)
  "留学"   → 命中 FAQ #1,2,3,5,6 (几乎所有问答)
  "学费"   → 命中 FAQ #1,4     (费用相关问答)
  "费用"   → 命中 FAQ #1,4
  候选集: {#1(命中4词), #2(命中2词), #3(命中1词), #4(命中3词), #5(命中1词), #6(命中1词)}
  
Step 4 — 逐条打分:
  FAQ #1 "德国双元制教育费用是多少":
    coverage: 同义词覆盖 4/5 × 高IDF + n-gram覆盖 1/3 × 低IDF ≈ 0.76
    jaccard: |{德国,留学,学费,费用} ∩ FAQ#1_tokens| / |并集| ≈ 0.42
    hit_bonus: (4×3 + 1) / (5×3 + 3) × 0.15 ≈ 0.11
    substring: "德国" 在问题中 → +0.3
    faq_score = 0.76×0.45 + 0.42×0.15 + 0.11 + 0.3 = 0.82 ✓ 最佳匹配

  FAQ #4 "新加坡留学一年费用":
    coverage: 同义词覆盖 3/5 × 中IDF ≈ 0.45 (无"德国"降低了IDF覆盖)
    jaccard ≈ 0.20
    hit_bonus ≈ 0.07
    substring: 无精确匹配 → +0
    faq_score = 0.45×0.45 + 0.20×0.15 + 0.07 + 0 = 0.30
  
  排序结果: FAQ #1 (0.82) > FAQ #4 (0.30) > ...

Step 5 — 返回:
  [{"source": "FAQ", "content": "Q: 德国双元制教育费用是多少\nA: ...", "score": 82}, ...]
  ↓ retrieve_context() 拼接
  "[来源: 中德精英人才共建计划_问答对]\nQ: 德国双元制教育费用是多少\nA: 德国双元制免学费..."
  ↓ 注入到 LLM prompt 作为参考资料
```

#### 为什么不使用 Embedding？

| 对比维度 | Embedding 方案 | 本方案（关键词+倒排索引） |
|---------|---------------|----------------------|
| 依赖 | sentence-transformers / torch (500MB+) | 纯 Python 标准库 |
| 启动时间 | 加载模型 5-30 秒 | 瞬间 |
| 可解释性 | 余弦相似度分数，难以解释为什么匹配 | 每一步都有明确原因（哪个词命中/IDF多少/Jaccard多少） |
| 领域适配 | 需要微调模型或 prompt 适配 | 直接改同义词映射和停用词白名单 |
| 检索延迟 | 需要向量计算（GPU 加速则快） | 倒排索引 O(k) 候选 + n-gram 对比，毫秒级 |
| 适用场景 | 开放域、长尾问题、语义相近但字面不同的查询 | FAQ 匹配型、教育/客服等有明确知识边界的领域 |

### 2.3 上下文工程

**没有使用微调（Fine-tuning），完全通过上下文工程实现意图控制和行为引导。**

#### 上下文工程手段汇总

| 手段 | 应用场景 | 实现方式 |
|------|---------|---------|
| System Prompt | 所有 Agent 的身份和行为约束 | 每个 Agent 独立 SYSTEM_PROMPT，定义身份/风格/能力边界 |
| Intent Descriptions | LLM 意图分类 | 9-10 种意图的自然语言描述，指导 LLM 输出结构化 JSON |
| 分场景 Prompt Template | 心理关怀/生活支持/增值转化/NL2SQL | 各自独立的 prompt 模板，含角色指导 + 输出格式约束 |
| 多轮状态注入 | 槽位填充 | SlotState 摘要注入对话流，让 LLM 知道"已收集什么、还缺什么" |
| RAG 上下文拼接 | FAQ/文档检索 | 检索到的 top-K 片段拼入 prompt 作为参考资料 |
| 风险分级指导 | 心理回复生成 | 根据 risk_level 注入不同的 risk_guidance 段落 |
| 角色权限注入 | 学生数据隔离 | NL2SQL prompt 明确"系统自动注入 student_id，你不要生成" |
| Low Temperature | 意图分类/信息提取/NL2SQL | temperature=0.1 保证输出稳定可解析 |

#### 典型 System Prompt 示例（客服 Agent）

```
你是"粤教服务"的智能客服助手"小粤"。
- 所属公司：广东省教育服务有限公司，成立于1981年
- 核心产品：新加坡国际本硕升学计划、中德精英人才共建计划
- 风格：专业、亲切、年轻化，像一位懂留学的朋友
- 回答原则：基于知识库不编造、不确定时引导转人工、涉及费用注明"以官方为准"
```

### 2.4 客户画像研判打分机制

**文件：** `utils/file_parser.py` → `assess_lead_intention()`  
**企业 Agent 版本：** `agents/enterprise/agent.py` → `_evaluate_profile()`

**方法：纯规则引擎打分（无 ML 模型），基于多维度的加权累加制。**

#### 整体流程

```
用户输入非结构化文本
  │
  ├─ Step 1: LLM 提取结构化字段
  │   model: GPT-4o-mini, temperature=0.1
  │   fields: [姓名, 性别, 年龄, 学历, 意向国家, 意向专业,
  │            家庭经济水平, 语言能力, 联系方式, 背景信息]
  │
  ├─ Step 2: 双项目独立打分
  │   ┌─ 新加坡项目评分 ─┐   ┌─ 德国项目评分 ─┐
  │   │ 年龄匹配   0-30  │   │ 年龄匹配   0-25  │
  │   │ 学历匹配   0-25  │   │ 学历匹配   0-20  │
  │   │ 国家意向   0-15  │   │ 国家意向   0-15  │
  │   │ 家庭经济   0-10  │   │ 语言水平   0-15  │
  │   │ 语言水平   0-5   │   │ 家庭经济   0-10  │
  │   │ 条件满足   0-15  │   │ 条件满足   0-15  │
  │   └─ 最高 100 分 ─┘   └─ 最高 100 分 ─┘
  │
  ├─ Step 3: 国家优先级处理
  │   意向国家="新加坡" → 德国归零
  │   意向国家="德国" → 新加坡归零
  │
  └─ Step 4: 判定
      ≥ 50 分 → 意向客户（取高分项目）
      < 50 分 → 暂不符合
```

#### 硬性否决条件

- 年龄 < 14 或 > 40 → 两个项目都归零，直接判定不匹配
- 学历不匹配特定项目 → 该项目不得分

### 2.5 心理监测打分机制

**文件：** `agents/student/psych_monitor.py`

**方法：两级评估体系 — 本地关键词快速检测（第一级）+ LLM 深度学习评估（第二级）**

#### 整体流程

```
学生消息
  │
  ├─ 第一级：本地关键词检测（零延迟）
  │   ├─ 高危词库（~18 个）：不想活/想死/自杀/自残/绝望/崩溃/被欺负...
  │   │   命中 → risk_level = "high", emotion_score = 5
  │   │        直接返回，不调用 LLM，保证高危场景秒级响应
  │   │
  │   ├─ 中危词库（~30 个）：失眠/孤独/焦虑/压力大/想哭/烦躁/迷茫/怕挂科...
  │   │   命中 → risk_level = "medium", emotion_score = 25
  │   │        继续进入第二级 LLM 精细评估
  │   │
  │   └─ 未命中 → {"emotion_tag": "未知", "emotion_score": 60, "risk_level": "none"}
  │               继续进入第二级
  │
  └─ 第二级：LLM 深度评估
      model: GPT-4o-mini
      temperature: 0.1
      max_tokens: 200
      prompt: PSYCH_MONITOR_PROMPT（含高危/中危信号定义）
      输出 JSON：
        - emotion_tag: 开心/焦虑/孤独/愤怒/沮丧/平静/期待
        - emotion_score: 0-100（0=极度负面，100=非常积极）
        - risk_level: high/medium/low/none
        - trigger_reason: 触发原因描述
      LLM 失败 → 回退到第一级结果
```

#### 高危信号定义（LLM prompt 中的定义）

```
risk_level=high：
  - 表达自杀/自伤想法
  - 严重抑郁描述（"活不下去""没有希望"）
  - 被欺凌/暴力描述

risk_level=medium：
  - 持续焦虑/失眠/睡不好描述
  - 明显孤独感/社交回避/不想与人交流
  - 学业压力大/作业写不完/怕挂科/跟不上
  - 情绪低落/持续伤心/状态不好/不知道怎么办
  - 想家/想哭/烦躁/无助
```

#### 分风险等级回复指导

| 风险等级 | emotion_score | 回复策略 |
|---------|---------------|---------|
| high | 0-10 | 极度温和，表达关心，建议联系专业心理咨询师或信任的老师。不轻描淡写，不回避问题 |
| medium | 11-40 | 表达理解和共情，肯定ta的感受，给一些缓解压力的小建议 |
| low | 41-70 | 用轻松温暖的语气回应，适当鼓励 |
| none | 71-100 | 正常友好地回应即可 |

#### 预警触发与记录

```
should_alert(evaluation):
  return risk_level in ("high", "medium")
  ↓
_record_alert():
  ├─ 写入 student_psych_alert 表（触发原因/风险等级/预警来源/状态）
  └─ 更新 student_psych_profile 表（最新情绪标签/分数/风险等级/累计次数）
```

**关键设计：所有意图都做轻量评估**

学生 Agent 的 `route_intent()` 中，无论用户输入被分类为哪种意图（请假/查成绩/闲聊等），都会旁路调用 `psych.evaluate()` 做心理评估。只有已经明确是心理关怀意图时才跳过（避免重复评估）。这确保了心理预警的全覆盖。

## 三、NL2SQL 安全机制

**文件：** `agents/enterprise/nl2sql.py`

**方法：多层白名单 + 黑名单校验，纯规则引擎，无 ML。**

| 层级 | 机制 | 详情 |
|------|------|------|
| 入口校验 | 必须 SELECT 或 UPDATE 开头 | 拒绝 INSERT/DELETE/DROP 等 |
| 黑名单词 | 词边界正则匹配 | DROP/ALTER/TRUNCATE/EXEC/INSERT/DELETE |
| 黑名单函数 | 子串匹配 | INTO OUTFILE/LOAD_FILE/SLEEP()/BENCHMARK() |
| 表白名单 | SELECT 的 FROM/JOIN 中的表 | 11 张可查表 |
| UPDATE 强制 | 必须有 WHERE + LIMIT | 防全表更新/批量误更新 |
| UPDATE 表白名单 | 仅 4 张表可更新 | crm_lead / feedback / admin_service / academic |
| UPDATE 列白名单 | 每表仅 4-5 个列 | 如 crm_lead 只能改 status/score/owner 等 |
| 学生隔离 | 自动注入 student_id 条件 | 清理 LLM 占位符后追加正确 ID |

## 四、多轮对话槽位填充

**文件：** `utils/conversation_state.py`

**方法：有限状态机（FSM）+ 三层逃生机制**

### 状态机

```
collecting → (is_complete) → confirming → (confirm) → done
                  ↑                │  (cancel) → cleared
                  │                │  (补充) → collecting
                  └────────────────┘
```

### 三层逃生（防死循环）

| 层 | 机制 | 原理 |
|----|------|------|
| 1 | 关键词检测 | 用户输入包含"查询/查看/成绩/活动"等 → 识别为话题切换 |
| 2 | LLM 语义判断 | `_llm_check_topic_switch()` 用 LLM 判断"补充"还是"新话题" |
| 3 | 交互计数 | 超过 5 轮 → 自动清状态，释放会话 |

## 九、关键设计决策

1. **不使用 Embedding 的原因**：项目面向教育服务场景，FAQ 问答对 + 同义词映射已能覆盖 90% 的查询。零外部依赖降低了部署门槛，且每条结果可追溯。

2. **不使用微调的原因**：GPT-4o-mini 的 zero-shot 能力已能满足意图分类和信息提取需求。通过精心设计的 prompt 即可控制行为，无需微调模型。

3. **双通道意图分类**：LLM 优先保证准确率，本地关键词兜底保证可用性（LLM 不可用时系统仍能工作）。

4. **所有意图覆盖心理评估**：学生 Agent 在每个意图处理中都旁路做心理评估，确保预警无死角。

5. **NL2SQL 列级白名单**：即使 LLM 生成了恶意 SQL，UPDATE 会被列级白名单拦截，SELECT 会被表白名单拦截。

## 十、待改进项与迭代方向

### 10.1 架构层面

#### 会话状态持久化（P0）

**现状**：槽位填充状态存储在模块级 `dict` 中。多 worker 部署（gunicorn）时，同一用户的连续请求可能被路由到不同 worker，导致状态丢失。

**方案**：将会话状态迁移到 Redis，key 为 `session:{id}`，TTL 自动过期。改动范围：`ConversationStateManager` 的 `_states` 替换为 Redis 读写。

```
现在: self._states: dict[str, SlotState] = {}
改进: redis.set(f"slot:{key}", json.dumps(state), ex=600)
```

#### 同步 HTTP 调用阻塞事件循环（P1）

**现状**：`requests.post()` 同步调用 LLM API。FastAPI 的 `def` 端点会自动丢进线程池，但换成 `async def` + `httpx.AsyncClient` 可以显著提升高并发吞吐。

**方案**：`LLMClient._call_api()` 改为 `async`，用 `httpx.AsyncClient` 复用连接池。涉及所有 Agent 的 handler 改为 async。

```
现在: def _call_api(self, messages) -> str: requests.post(...)
改进: async def _call_api(self, messages) -> str: await self.client.post(...)
```

#### 缺少 API 限流（P1）

**现状**：`/api/chat` 没有任何频率限制，可能被恶意刷接口消耗 LLM token。

**方案**：引入 `slowapi`（FastAPI 原生兼容），按 IP 或 user_id 限制每分钟请求次数。

### 10.2 RAG 检索进化路线

#### 第一阶段：当前状态 ✓

关键词 + 同义词 + 倒排索引 + IDF 加权。FAQ 型查询效果好，零依赖。

#### 第二阶段：混合检索（短期迭代）

**问题**：当前方案对"字面不同但语义相同"的查询无能为力。例如知识库中写的是"如何办理退费"，用户问"钱能拿回来吗"，关键词完全匹配不上。

**方案**：加一层轻量 Embedding 做语义召回，与关键词召回并行，结果合并排序。

```
候选 = 关键词倒排召回(top-K) ∪ 向量语义召回(top-K)
重排序 = 关键词分数 × 0.4 + 语义相似度 × 0.6
```

**推荐模型**：`BAAI/bge-small-zh-v1.5`（中文，仅 24MB），用 `sentence-transformers` 加载，CPU 即可推理。

#### 第三阶段：知识库在线更新（中期迭代）

**问题**：目前知识库是启动时一次性加载到内存，新增 FAQ 需要重启服务。

**方案**：增加 `/api/admin/kb/reload` 热重载接口，或监听文件变更自动增量更新索引。

### 10.3 Agent 代码重构

#### 抽取公共基类（P1）

**现状**：三个 Agent 的 `continue_data_collection` 方法 ~300 行代码几乎完全相同（取消检测 → 确认阶段 → 收集阶段 → 话题切换 → 交互计数兜底），大量复制粘贴。

三个 Agent 的 `_handle_feedback` 在 customer 和 student 中也 ~80% 重复。

**方案**：

```python
class BaseAgent:
    def continue_data_collection(self, user_input, state, user_ref, db):
        """通用槽位填充，子类只需实现 _extract_for_intent 和 _commit_collected"""
        # 统一的取消/确认/收集/逃生逻辑
        ...
    
    @abstractmethod
    def _extract_for_intent(self, user_input, intent): ...
    
    @abstractmethod
    def _commit_collected(self, state, user_ref, db): ...
```

**收益**：删除 ~500 行重复代码，后续新增 Agent 只需关注业务逻辑。

### 10.4 数据库与查询优化

#### 列表接口加分页（P2）

**现状**：`EventCRUD.get_all()`、`CrmCRUD.get_all()` 等全量返回，数据量大时内存和响应时间都会膨胀。

**方案**：增加 `limit/offset` 参数，返回 `{items, total, page, page_size}`。

#### 活动报名防重复（P2）

**现状**：`event_registration` 表没有唯一约束，同一客户可对同一活动重复报名。

**方案**：加联合唯一索引 `(event_id, customer_id)` 或 `(event_id, contact)`。

#### 活动查询按时间排序（P2）

**现状**：`EventCRUD.get_all()` 按 `start_time DESC` 排序，已结束的旧活动也会排在前面（虽然 Agent 层已过滤状态）。建议在 SQL 层加 `event_status` 过滤和按 `start_time ASC`（最近的优先）。

### 10.5 功能闭环补完

#### "回复编号报名"功能未实现（P1）

**现状**：`_handle_event_registration` 返回文案"回复活动编号（如「1」）即可报名"，但用户回复数字并不会触发报名流程——会走意图分类被当成闲聊或 FAQ。

**方案**：
1. 在 `route_intent()` 中检测纯数字输入（1-20）且有活跃的活动列表上下文
2. 调用 `EventCRUD.register()` 完成报名
3. 需要在 `SlotState` 中记录最近一次展示的活动列表

#### 知识库覆盖范围

**现状**：FAQ 集中在公司信息、项目介绍、政策指南。以下领域知识库为空或薄弱：
- 留学申请具体流程（文书怎么写、推荐信找谁）
- 各国签证材料清单（英国/美国/加拿大）
- 费用明细与奖学金
- 学生常见心理问题的自助指南

### 10.6 可观测性

#### 统一日志规范（P1）

**现状**：只有 NL2SQL 查询失败和心理预警记录有 logging，大部分异常只返回字符串，线上排查困难。

**方案**：
- 所有 Agent handler 的 `except` 分支加 `logger.error()`，含上下文（user_id/student_id/原始输入）
- 接入结构化日志（JSON 格式，方便日志平台检索）
- 关键路径加 `logger.info()`：意图分类结果、RAG 检索耗时、LLM 调用耗时

#### 增加指标埋点（P2）

建议埋点位置：

| 指标 | 位置 | 用途 |
|------|------|------|

| 槽位填充成功率 | `ConversationStateManager` | 监控多轮对话完成率 |
